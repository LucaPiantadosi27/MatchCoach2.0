5. FLUSSO DI FUNZIONAMENTO

Registrazione:
  Client → POST /api/auth/register (email, password) →
  Validazione → Hash password → Crea user → Genera JWT pair →
  Hash refresh token → Salva in DB → Ritorna tokens

Login:
  Client → POST /api/auth/login (email, password) →
  Trova user → Verifica password → Genera JWT pair →
  Aggiorna refresh token → Ritorna tokens

Refresh:
  Client → POST /api/auth/refresh (Bearer refresh_token) →
  Valida JWT refresh → Estrai userId → Verifica hash in DB →
  Genera nuovi tokens → Aggiorna refresh token

Storage upload:
  Client → Richiede presigned URL → Upload diretto a MinIO

6. API / ENDPOINT

GET  /api/health           — Health check (no auth)
POST /api/auth/register    — Registrazione (body: email, password, firstName?, lastName?)
POST /api/auth/login       — Login (body: email, password)
POST /api/auth/refresh     — Refresh token (header: Bearer <refresh_token>)
POST /api/auth/logout      — Logout (header: Bearer <access_token>)

7. MODELLO DATI

11. DECISIONI TECNICHE

- Prisma 7: versione più recente disponibile, richiede prisma.config.ts
  separato per la configurazione della datasource URL.
- CommonJS module: scelto per compatibilità con l'ecosistema NestJS,
  che non supporta ancora pienamente ESM con nodenext.
- bcrypt 12 rounds: compromesso sicurezza/performance per dev singolo.
- Refresh token hashato in DB: impedisce riuso anche in caso di leak.
- pgvector abilitato da subito: necessario per Macrostep 7 (embedding).
- Docker pgvector/pgvector:pg16: immagine ufficiale con estensione pre-installata.
- Global prefix /api: separazione chiara tra API e eventuali asset statici.
- StorageService globale: riusabile da qualsiasi modulo senza reimportare.
