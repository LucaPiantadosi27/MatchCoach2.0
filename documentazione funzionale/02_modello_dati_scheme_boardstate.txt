3. MODULI IMPLEMENTATI

Modulo 2.1 — User/Team
  - Model Team con owner e members
  - Model TeamMember (relazione many-to-many user-team)
  - Model TeamPlayer (rosa giocatori con numero e posizione)
  - Model Season (stagioni con date)
  - TeamsService: createTeam, findTeamsByUser, findTeam, addPlayer, removePlayer
  - TeamsController: CRUD endpoints protetti da JwtAuthGuard
  - Ownership verification su operazioni di modifica

Modulo 2.2 — Scheme
  Entità unificata:
    Scheme
    ├── type: STATIC (formazione fissa)
    └── type: RECORDING (con keyframes)
  
  Campi principali:
    - boardState (Json) — lo stato della lavagna
    - recording (Json?) — i keyframes se type=RECORDING
    - contractVersion — versione del contratto dati
    - tags — etichette per organizzazione/ricerca
    - snapshotKey — riferimento PNG su MinIO
  
  Relazione 1:1 con SchemeInsight (preparata per Macrostep 7)

Modulo 2.3 — BoardState (v2.0)
  Interfaccia formale:
    BoardState {
      version: "2.0"
      players: PlayerState[]
      paths: DrawingPath[]
      meta?: BoardStateMeta
    }
  
  PlayerState:
    - id: string
    - team: "A" | "B"
    - number: 1–99
    - x: 0.0–1.0 (normalizzato)
    - y: 0.0–1.0 (normalizzato)
    - rotation: 0–360
    - label?: string
  
  DrawingPath:
    - id: string
    - type: "line" | "arrow" | "freehand"
    - points: Array<{x, y}> (normalizzati)
    - color?: string
    - strokeWidth?: number

Modulo 2.4 — MovementRecording (v1.0)
  Interfaccia formale:
    MovementRecording {
      version: "1.0"
      duration: number (ms)
      initialState: PlayerKeyframe[]
      keyframes: Keyframe[]
    }
  
  Keyframe:
    - timestamp: number (ms, crescente)
    - players: PlayerKeyframe[]
  
  PlayerKeyframe:
    - playerId: string
    - x: 0.0–1.0
    - y: 0.0–1.0
    - rotation: 0–360

Modulo 2.5 — Validazione
  validateBoardState():
    - version supportata (1.0, 2.0)
    - players è array
    - ogni player: id, team A/B, number 1-99, x/y 0-1, rotation 0-360
    - paths opzionale ma se presente: id, type valido, points con coords 0-1
  
  validateMovementRecording():
    - version supportata (1.0)
    - duration > 0
    - initialState: array di PlayerKeyframe validi
    - keyframes: array ordinato per timestamp crescente
    - timestamp non supera duration
    - ogni PlayerKeyframe: playerId, x/y 0-1, rotation 0-360

Modulo 2.6 — Versioning
  - BoardState: version "2.0" (supportata anche "1.0" per compatibilità)
  - MovementRecording: version "1.0"
  - Scheme.contractVersion: campo esplicito per tracciare la versione
  - I validatori controllano le versioni supportate
  - Nuove versioni possono essere aggiunte senza rompere le precedenti

5. FLUSSO DI FUNZIONAMENTO

Creazione schema:
  Client → POST /api/schemes (boardState + recording?) →
  DTO validation (class-validator) →
  BoardState structural validation →
  MovementRecording validation (if present) →
  Determine type (STATIC/RECORDING) →
  Prisma create → Response

Aggiornamento schema:
  Client → PUT /api/schemes/:id →
  Ownership check →
  Validazione campi modificati →
  Update

6. API / ENDPOINT

Schemes:
  POST   /api/schemes           — Crea schema (auth required)
  GET    /api/schemes           — Lista schemi utente (?teamId, ?seasonId, ?tags)
  GET    /api/schemes/count     — Conteggio schemi utente
  GET    /api/schemes/:id       — Dettaglio schema (con insight)
  PUT    /api/schemes/:id       — Aggiorna schema
  DELETE /api/schemes/:id       — Elimina schema

Teams:
  POST   /api/teams             — Crea team
  GET    /api/teams             — Lista team utente
  GET    /api/teams/:id         — Dettaglio team (con players e members)
  POST   /api/teams/:id/players — Aggiungi giocatore
  DELETE /api/teams/:id/players/:playerId — Rimuovi giocatore (soft delete)
  DELETE /api/teams/:id         — Elimina team

11. DECISIONI TECNICHE

- BoardState come Json in Prisma: la struttura è validata a livello
  applicativo (non DB constraint), permettendo flessibilità ed evoluzione.
- Coordinate normalizzate 0-1: indipendenti dalla risoluzione del device,
  permettono rendering su qualsiasi dimensione di schermo.
- Validazione separata dai DTO: i DTO (class-validator) verificano la
  struttura esterna, i validator custom verificano la semantica interna
  del boardState/recording.
- SchemeInsight con Unsupported("vector(768)"): Prisma non gestisce
  nativamente pgvector, usiamo Unsupported per dichiararlo nello schema
  senza generare metodi Prisma — le query vector saranno raw SQL.
- TeamPlayer soft delete (active=false): preserva storico schemi associati.
- Ownership check nel service, non nel guard: permette logica più fine
  (es. team members possono leggere ma non modificare).

12. LIMITAZIONI NOTE

- SchemeInsight.embedding usa Unsupported: le operazioni su pgvector
  richiederanno query raw ($queryRaw) nel Macrostep 7.
- Non c'è ancora un endpoint per la ricerca semantica (verrà in MS7).
- Il campo snapshotKey non è ancora popolato (verrà in MS3 con la lavagna).
- I tag sugli schemi non hanno autocomplete/suggerimenti lato server.
