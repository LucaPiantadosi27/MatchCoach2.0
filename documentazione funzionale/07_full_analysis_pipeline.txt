1. OBIETTIVO

Collegare i componenti sviluppati nei macrostep 5 e 6 in una pipeline
completa e asincrona: dallo Schema salvato, eseguire MovementAnalysisEngine,
passare il report a GeminiService e persistere il risultato in
SchemeInsight. Esporre un endpoint REST per avviare l'analisi via worker
BullMQ.

2. FUNZIONALITÀ IMPLEMENTATE

- Modulo `AnalysisModule` registrato in AppModule
- Endpoint `POST /api/schemes/:id/analyze` protetto da JWT
- `AnalysisService` che accoda un job nella coda `scheme-insight`
- `AnalysisProcessor` (BullMQ worker) che esegue:
  * recupero dello Schema da Prisma
  * esecuzione di MovementAnalysisEngine
  * invocazione di GeminiService per l'interpretazione
  * upsert di SchemeInsight con descrizione, tag, metriche, modello, token
- Integrazione con QueueModule e Redis esistenti
- Persistenza delle metriche di movimento in JSON

3. MODULI IMPLEMENTATI

Modulo 7.1 — AnalysisModule
  - imports: QueueModule, PrismaModule, GeminiModule
  - controller: AnalysisController
  - providers: AnalysisService, AnalysisProcessor

Modulo 7.2 — AnalysisController
  - `POST /api/schemes/:id/analyze`
  - @UseGuards(JwtAuthGuard)
  - @CurrentUser per ownership check
  - Restituisce { jobId, schemeId, status: 'queued' }

Modulo 7.3 — AnalysisService
  - Verifica esistenza e ownership dello Scheme
  - Accoda job `analyze` nella coda `scheme-insight`
  - Rimuove job completati, conserva quelli falliti

Modulo 7.4 — AnalysisProcessor
  - Estende WorkerHost di @nestjs/bullmq
  - `@Processor('scheme-insight')`
  - Processa `AnalyzeJobData { schemeId, userId }`
  - Recupera boardState e recording dallo Scheme
  - Se il recording è assente, costruisce uno stato iniziale dal board
  - Esegue MovementAnalysisEngine
  - Esegue GeminiService
  - Upsert di SchemeInsight via Prisma

5. FLUSSO DI FUNZIONAMENTO

Richiesta:
  Client → POST /api/schemes/:id/analyze (JWT)
  → AnalysisController → AnalysisService
  → Verifica ownership
  → Aggiunge job a scheme-insight queue
  → Redis + BullMQ
  → Worker AnalysisProcessor
  → Recupera Scheme da PostgreSQL
  → MovementAnalysisEngine produce report
  → GeminiService produce interpretazione
  → Prisma SchemeInsight.upsert
  → Restituisce { jobId, schemeId, status: 'queued' }

6. API / ENDPOINT

POST /api/schemes/:id/analyze
  Headers: Authorization: Bearer <token>
  Response:

11. DECISIONI TECNICHE

- Worker nel processo principale: per dev è sufficiente, in produzione
  si passerà a un processo worker separato (Macrostep 13)
- Coda `scheme-insight` pre-registrata in QueueModule
- Upsert di SchemeInsight: mantiene 1:1 con Scheme
- Embedding pgvector non popolato: lasciato a schema Unsupported per MS9 RAG
- Ownership check lato service: evita accodare job su risorse altrui
- Job id deterministico `analyze-<schemeId>`: evita duplicati
- Import assoluti `src/...`: hanno risolto problemi di risoluzione moduli
  nelle sottocartelle `analysis/services` e `analysis/processors`

12. LIMITAZIONI NOTE

- Worker non è un processo separato (solo dev)
- Nessun test E2E della coda (richiede Redis)
- Embedding non generato (servirà pgvector + modello di embedding in MS9)
- Nessuna gestione avanzata di retry o rate limiting
- Nessun endpoint GET per lo stato del job
- Il fallback Gemini è usato se la chiave non è configurata
